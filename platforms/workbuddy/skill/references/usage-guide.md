# 使用说明

skill-failure-auditor（SFA）用于审阅大语言模型或智能体的指令、能力定义、执行链和已经产生的运行材料。它寻找假完成、自我验收、验收标准改写、证据完整性和职责独立性等可靠性失效。普通源码审阅、发布检查、安装排错和目标实现不属于它的诊断范围。

## 最短调用

正式诊断需要给出待审路径、审计模式和一个尚不存在的输出目录。三种模式按材料选择：

- `static`：只审阅指令、合同和能力定义，不验证运行表现。
- `runtime`：只审阅已经产生的日志、工具输出和回执，不启动目标补证。
- `combined`：同时审阅静态定义和已有运行材料。

用户显式指定模式时，入口保留该模式。若材料与显式模式不匹配，入口报告缺项和继续条件，不把请求改成另一模式。只有用户没有指定模式时才按材料选择：只有一类材料时选择对应模式，两类材料都存在时选择 `combined`；材料不足以区分时，入口只询问这一项必要差异。

```text
使用 skill-failure-auditor，对 <待审路径> 做 <static|runtime|combined> 可靠性失效审计，只读目标，把产物写入 <新的输出目录>。
```

该调用会运行 SFA 自身的登记表、证据和结果校验工具，并在调用方指定的新目录写入审计材料。它不会运行、修复或改写被审目标，不会派发子智能体，也不会接入目标的实时控制过程。

## 使用前提检查

准备度检查只回答当前环境能否使用 SFA，不开始诊断。检查项包括：

- 可用的 Python 3 解释器；
- 已设置的 `SFA_FOUNDATION_NODE`；其值必须是 Node.js 可执行文件的无软链绝对实路径；
- 该实路径执行 `--version` 的结果精确匹配 `foundation/foundation-pin.json` 记录的 Node.js 版本；
- 与所选模式对应的可读材料；
- 调用方明确给出的新输出目录。

检查可以查询解释器自身版本并读取现有文件。`SFA_FOUNDATION_NODE` 缺失、路径不是无软链绝对实路径或版本不匹配时，必须列为继续条件。其他依赖或材料缺失时也列出真实缺项；环境已经兼容时保持现状。该分支不安装或升级依赖，不创建目标脚手架，不运行目标，也不生成审计尝试或报告。

## 接入分析

接入分析适合回答“当前项目还缺什么”。它说明已经满足的前提、缺项、保持现状或采用有来源方案的影响。SFA 没有修改目标工程或安装环境的接入能力；用户授权实施时，应交给实际提供安装、依赖或编排能力的工具处理。

SFA 是可独立请求的诊断工具，不要求所有项目都接入 Audit，也不产生统一证明文件。帮助、准备度检查和接入分析都在给出说明后结束，其成功不等于审计成功。

## 交付范围

诊断只依据冻结输入。静态诊断没有验证运行表现；运行材料中的观察只适用于材料实际记录的模型、版本、配置、任务、时间和环境。材料没有记录的事实保持未知，不能从模型 A 的材料推断模型 B，也不能把一次运行推广到后续运行。

报告中的整改建议说明已观察故障、证据理由和直接解决该故障的最小修改。`next_probe` 只表示后续可考虑的验证动作，不会自动启动探针、修复或下一轮审计。

## 发布记录核对

SFA 的研发发布检查仍由项目原有流程负责。治理场景如需离线核对既有发布记录，使用 release-skill 0.9.19 的 `verify-records`，并由调用方显式提供 plan、approval、target-run、每一份 source-run、期望 unit 和历史版本。命令不搜索记录、不跟随记录内的路径、不联网、不运行 hooks，也不写文件。

`CONSISTENT`、`CONTRADICTED`、`INSUFFICIENT` 的退出码分别为 0、1、2；`historicalTerminalStatus` 是独立维度。历史记录一致只能说明这些显式记录彼此相容，不能证明当前远端状态、安装效果或记录集合是全局最新。缺少必需路径时先向调用方索取，不能搜索或编造输入。
