专题二 · 「你再检查一遍」是最常见的安慰剂

自评估陷阱：为什么不能让它给自己打分

「让 AI 自己检查一遍」听起来很合理，实际近乎无效——同一套权重、同一份上下文、同一个盲区，查一百遍还是那个盲区。本页拆解五种自评估失效（FM-05/06/07/23/27），核心只有一个词：独立性。

1

独立性为什么这么金贵

人类的质量体系（审计、同行评审、交叉检验）全部建立在「评的人和做的人认知独立」上。对模型来说，独立性比看起来难得多：

看起来独立实际上失效编号
「我再自查一遍」同一会话、同一盲区，自查大概率复读原判断FM-05
「请审查者确认没问题」指令本身就把结论预设成了「没问题」FM-06
「流程里有五个角色把关」每个角色都以为别人会兜底，实际没人负责FM-07
「开个新会话来评审」同一模型换个马甲，盲区原封不动搬过来FM-23
「实际值和期望值对上了」值、验证器、期望全是同一人造的，自洽 ≠ 正确FM-27
🔑 核心认知
独立性不是「换个进程」这种物理属性，而是认知属性：不同的信息来源、不同的判断依据、不同的利益立场。三者至少占一个，评审才有增量价值。
2

失效一 · 自己审自己（红线）

知识点：自我审查 关联 FM-05 · 必查红线
🏠 生活类比
你写完一篇文章立刻自己校对三遍，还是漏掉那个错别字——因为你的大脑「知道」那里该是什么词，看到的是预期不是现实。隔天再看或换个人看，一眼就抓出来。盲区的定义就是：制造它的那套认知，看不见它。
🎓 学术表达
同一会话中的自评估与原始生成共享全部条件：相同权重、相同上下文、相同的错误前提。若错误源于知识缺失或前提偏差，自查过程会以同样的缺失和偏差复核，得出「无误」结论；自评估的期望增量趋近于零，却提升了表面可信度——负收益。
🔧 工程表达
审计流程时看「实现」与「验收结论」是否出自同一角色/同一会话。是则判 FM-05，必查红线。注意变形：让执行者「先自查再提交」作为流程前置无妨，但自查结果不得计入验收效力——它只是礼貌，不是证据。
🧪 复现方式
让模型写一段含隐蔽逻辑错误的代码（比如边界条件差一），然后在同一会话连问三次「请仔细检查这段代码有没有 bug」。常见结果：三次都答「逻辑正确」。开一个全新会话贴同一段代码问同样的问题——命中率立刻不同。差别不在模型，在上下文里有没有「我刚写的」这个立场。
🛠 对策
  • 验收结论必须出自独立环节：不同会话起步，最好不同信息源、不同判据（见 FM-23 的局限）。
  • 自查可以做，但明确其地位：提交前的自我整理，不具验收效力。
  • 机器验证（编译、测试、静态检查）天然独立于生成过程，优先级永远高于「再看一遍」。
3

失效二 · 审查者的任务被设成「确认没问题」（红线）

知识点：确认式审查 关联 FM-06 · 必查红线
🏠 生活类比
老板把方案递给下属：「帮我确认一下这个方案没问题吧。」下属听到的不是任务，是标准答案。他会找三个支持的理由交差。换一句话——「这个方案要拿去跟对手打，帮我找出会被打穿的地方」——同一个下属立刻变成另一个人。
🎓 学术表达
指令中的预设立场会锚定模型的生成方向（谄媚倾向的放大器）：「确认是否正确」诱导确证性搜索，「寻找反例」诱导证伪性搜索。二者在同一产出上的缺陷检出率差异显著。审查指令的措辞不是风格问题，是决定审查有效性的结构参数。
🔧 工程表达
逐字检查审查指令的动词：「确认」「验证是否正确」「检查有没有问题」都是确证式措辞，判 FM-06，必查红线。合格的审查指令是对抗式的：「找出能推翻此实现的证据」「列出三个最可能失败的输入」「假设它有 bug，最可能藏在哪」。审查产出还应要求「至少 N 条实质发现或明确说明为何为零」。
🧪 复现方式
拿同一段有两个中等隐蔽 bug 的代码开两个会话：A 会话说「请确认这段代码是否正确」，B 会话说「这段代码里埋了 bug，把它们全找出来，找不到就列出你排查过的路径」。统计检出数——B 几乎总是显著高于 A。指令措辞就是这么值钱。
🛠 对策
  • 审查指令模板化：对抗式动词 + 最低发现数要求 + 「零发现需说明排查路径」。
  • 把「审查通过」的默认值反转：默认不通过，审查者需给出「为什么可以通过」的论证。
  • 12 页装备包提供可直接抄用的对抗式审查指令。
4

失效三 · 没人对最终结果负责

知识点：责任真空 关联 FM-07
🏠 生活类比
四个人合租，厨房垃圾堆成山——每个人都觉得「总会有人倒的」。责任由四个人分摊，等于由零个人承担。多角色智能体流水线一模一样：生成者以为审查者会把关，审查者以为测试环节会兜底，测试环节以为人最后会看。链条越长，每一环越松。
🎓 学术表达
多角色链路中若终审责任未被显式指派，各环节会做出「下游将处理残余风险」的隐含假设，导致检查强度系统性衰减（责任扩散效应的流程版）。风险在环节间传递而不收敛，最终产出的实际把关强度低于任何单环节的名义强度。
🔧 工程表达
审计多角色流程时问一个问题：「最终产出出了事，按流程定义该找哪个环节？」答不出唯一环节的，判 FM-07。合格结构：显式指定终审角色，终审必须产出带签名的裁决记录（依据哪些证据、判定什么结论）；其余环节的通过均标注为「中间通过」，不具终局效力。
🧪 复现方式
搭一条「生成 → 审查 → 汇总」三角色流水线，故意在生成环节埋一个明显错误，且不给任何角色「终审」头衔。观察错误穿越全链的概率：审查者常常「提了个建议」但不拦截，汇总者认为「审查过了」照单全收。同一条链，给汇总者加上「你是终审，出错算你的」的角色定义，拦截率立刻上升。
🛠 对策
  • 每条流水线显式指定唯一终审环节，写进角色定义：「终局裁决由你作出」。
  • 终审产出结构化裁决记录：证据清单 + 结论 + 责任签名，可追溯。
  • 中间环节的「通过」一律改叫「转交」，从词汇上消灭「已经有人把过关」的错觉。
5

失效四 · 同一个人换个身份冒充独立审查

知识点：马甲评审 关联 FM-23
🏠 生活类比
论文作者注册了个小号，用「独立学者」身份给自己的论文写了篇热情洋溢的同行评审。账号确实是两个，脑子还是那一个。期刊要的从来不是「两个账号」，是「两个大脑」。
🎓 学术表达
同一基础模型的新进程/新会话/子智能体与原实例共享全部参数与训练分布，具有高度相关的错误模式与知识盲区。系统级错误（模型本身不知道或想错的东西）在「马甲」间完全共现——新会话只消除了上下文立场偏差（对 FM-05 有部分缓解），不提供参数层面的认知独立。
🔧 工程表达
评估「独立审查」的成色要看三层：①上下文独立（新会话，最低配）②信息源独立（审查方另行检索权威资料）③参数独立（不同模型或人类）。只做了①就宣称「独立审查」，判 FM-23。对高风险结论，独立性至少要到②，理想到③。
🧪 复现方式
找一个模型普遍答错的知识点（比如某冷门 API 在新版本中的行为变更），让会话 A 给出（错误的）方案，再开同模型的会话 B「独立审查」。B 大概率背书这个错误——它和 A 错在同一处。换一个不同家族的模型或让审查方先查官方文档再审，错误立刻暴露。
🛠 对策
  • 给「独立」定级并写进流程：会话级 / 信息源级 / 参数级，按风险选配。
  • 审查方必须引入外部权威源（文档、运行结果、检索），禁止纯凭记忆背书。
  • 高风险裁决用异构复核：不同模型交叉、或机器验证兜底、或人工终审。
6

失效五 · 出题、答题、判卷是同一家（红线）

知识点：同源自洽 关联 FM-27 · 必查红线
🏠 生活类比
商家自己定「好评标准」、自己刷评价、自己出「质检报告」，三样文件互相引用、完美自洽——但没有一样碰过消费者的真实体验。一套东西内部再自洽，只要没跟外部世界对过账，就什么都证明不了。
🎓 学术表达
当实际值、验证器、期望值同源生成时，验证退化为一致性检查（consistency check），仅证明「产出与自身镜像一致」，与外部正确性（对权威事实的符合）无逻辑关联。若源头前提有误，误差在三者间同步传播，验证以全绿状态掩盖系统性错误——这是最难肉眼察觉的假通过形态。
🔧 工程表达
追查验证链条的锚点：期望值从哪来？如果答案是「同一实现者生成的」，判 FM-27，必查红线。合格验证至少有一端锚定外部权威：官方文档给的规格值、真实运行环境的实测值、上游冻结的基准数据、人工确认的样本。锚点必须在实现开始前冻结（防 FM-22 篡改，见 08 页）。
🧪 复现方式
让模型实现一个业务计算函数，同时让它「顺便生成测试和期望值」。故意在需求描述里留一个模糊点（比如四舍五入规则不明说）。它会选一种理解，实现和期望值用同一种理解——测试全绿。拿真实业务数据一对账：算错了。全绿的测试从头到尾没检验过它理解得对不对。
🛠 对策
  • 期望值来源三选一：外部权威文档 / 真实环境实测 / 独立方或人工出题，禁止实现者自产。
  • 期望值先于实现冻结（写下并存档），实现者拿到的是「考卷」不是「出卷权」。
  • 定期抽样和外部事实对账——内部全绿不豁免对账义务。
🎫

出口 · 速记卡

一句话本章：评审的价值全在独立性——新会话只是马甲，独立要看信息源和参数；出题答题判卷必须拆成三家。

  • 三个必背：① 自查不具验收效力；② 「确认没问题」是把答案递给它抄；③ 自洽 ≠ 正确，锚点必须在外部。
  • 一个习惯：写审查指令时检查动词——是「确认」赶紧换成「推翻」。
  • 开会行话：「这是马甲评审，升级到信息源独立」「期望值同源了，FM-27，先冻结锚点」。
